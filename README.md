## Назначение
Демон управляет устройствами умного дома через шину RBUS, Modbus и другие протоколы. Процесс поднимает сетевые сервисы, синхронизирует состояние устройств, исполняет скрипты и маршрутизирует команды между локальной сетью, удаленными клиентами и облачными сервисами (Janus, SIP, push-уведомления).

## Архитектура
- **Входная точка**: `daemon.js` инициализирует файловую структуру (`src/assets`), открывает локальную базу (`src/db.js`), восстанавливает состояние, запускает контроллеры, драйверы и сетевые сервисы.
- **Состояние и действия**: модуль `src/controllers/state.js` хранит оперативное состояние в памяти, а `src/actions/*` предоставляет CRUD-операции, биндинги и счетчики устройств. Постоянное хранилище реализовано на LevelDB (`var/db`).
- **Контроллеры**: `src/controllers` инкапсулируют доменную логику:
  - `device` управляет устройствами и их жизненным циклом;
  - `service` исполняет команды, расписания, таймеры и взаимодействует с драйверами;
  - `cpu` следит за системными ресурсами;
  - `weather` агрегирует внешние данные.
- **Драйверы**: каталог `src/drivers` содержит адаптеры для RBUS, Modbus TCP, ArtNet, DALI и специализированных устройств HVAC, освещения и мультимедиа. Обработка ведется через `drivers.manage()` и `drivers.run()`.
- **Сетевые сервисы**:
  - `src/discovery.js` рассылает мультикаст-объявления для локального обнаружения;
  - `src/websocket` поднимает локальный WebSocket на 3000 порту и подключается к удаленному шлюзу `wss://gate.reacthome.net`;
  - `src/janus` и `src/sip` отвечают за медиасервисы и телефонию;
  - `src/notification` отправляет уведомления через APN и Firebase.
- **Ассистент и вспомогательные модули**: `src/assist` реализует обработку естественного языка и поиск команд (Levenshtein). Каталог `src/assets` поддерживает директории `var/assets`, `var/tmp`, `var/db`.

## Поток управления
1. При старте демон восстанавливает состояние устройств и запланированных задач из LevelDB.
2. Контроллер `service` активирует таймеры, расписания, shell-скрипты и настраивает стартовые сценарии проекта.
3. Драйверы поддерживают соединения с устройствами (серийные порты, TCP-сокеты, UDP), нормализуют ответы и публикуют события в хранилище.
4. WebSocket-сервер обеспечивает локальный UI/API, а удаленный шлюз транслирует события внешним клиентам.
5. Уведомления, SIP и Janus получают доступ к состоянию через `src/actions` и `src/controllers`.

## Работа по сокету
- **Транспорт**. UDP-сокет создается оберткой `src/sockets/socket.js`: демон слушает `DEVICE_SERVER_PORT` (2016) на интерфейсе `172.16.0.1`, отправляет пакеты на порт `DEVICE_PORT` (2017). Все операции сериализуются через очередь с шагом 3 мс, чтобы не перегружать сеть.
- **Открытие устройства**. Каждый 10-секундный цикл отправляется мультикаст-пакет обнаружения в группу `DEVICE_GROUP` (`224.0.0.1`). Структура пакета: 1 байт кода `ACTION_DISCOVERY` (`0xF0`), 4 байта IP-адреса демона в формате BE, 2 байта номера порта. Пример: для адреса `172.16.0.1` и порта `2016` отправляется последовательность `f0 ac 10 00 01 07 e0` (hex).
- **Ответ устройства**. Любой контроллер отвечает унифицированным фреймом: 6 байт MAC, 1 байт кода действия, далее полезные данные. Первичный отклик (`ACTION_DISCOVERY` или `ACTION_READY`) содержит тип устройства и версию прошивки (`type`, `major`, `minor`). Пример ответа диммера версии `1.2`: `01 23 45 67 89 ab f0 0f 01 02`.
- **Рабочие команды**. Безхедерные пакеты направляются на IP устройства (устройство сохраняется через `online()` во время обработки ответа). Форматы нагрузок определяются кодом действия:
  - Прямое управление: `[ACTION_DO, index, value]` переключает реле, `[ACTION_RGB, index, r, g, b]` управляет светодиодом и т. п.
  - Режимы, таймеры и градиенты дополняются параметрами времени, групп или скоростей (например, `ACTION_DO` с дополнительными 4 байтами таймаута в миллисекундах).
- **Маршрутизация RBUS**. Для устройств, подключенных через концентраторы, используется обертка `device.sendRBUS`. Заголовок включает `ACTION_RBUS_TRANSMIT` (`0xA1`) и MAC целевого устройства; при наличии хаба добавляются порт и адрес. Пример команды включения выхода 3 через RBUS: `a1 01 23 45 67 89 00 03 01`.
- **Связка Smart TOP/Bottom**. Верхние панели управляются командой `ACTION_SMART_TOP` (0x30), упакованной в RBUS: `device.sendTOP` строит полезную нагрузку и перенаправляет ее через «нижний» блок.
- **Прием данных**. Обработчик `device.handle()` декодирует `ACTION_DI`, `ACTION_DO`, `ACTION_TEMPERATURE`, `ACTION_CO2`, `ACTION_SMART_TOP`, `ACTION_ERROR` и другие события, обновляя состояния каналов и инициируя сценарии. Логика модульна: новые типы сообщений добавляются через расширение `switch` в `src/controllers/device.js`.

## Работа по вебсокету
- **Эндпоинты**. Локальные клиенты подключаются к `ws://<host>:3000`, удалённые — через `wss://gate.reacthome.net/<mac>` с протоколом `listen`. На локальном сервере каждое подключение получает UUID-сеанс; через шлюз сообщения проксируются с префиксом из 36 символов (UUID), за которым следует JSON полезная нагрузка.
- **⚠️ ВАЖНО: Gateway и session ID**. При работе через удалённый gateway (`wss://gate.reacthome.net`) **клиент НЕ должен добавлять session ID** к сообщениям. Gateway сервер сам добавляет session ID при маршрутизации к демону. Если клиент также добавит session ID, получится двойной префикс, что приведёт к ошибкам парсинга JSON на стороне демона (`SyntaxError: Unexpected token`). Клиент должен отправлять чистый JSON без префиксов:
  ```json
  {"type": "ACTION_SCRIPT_RUN", "id": "script-uuid"}
  ```
  Gateway автоматически добавит session ID: `{session_id}{json_message}`.
- **Жизненный цикл сеанса**. Подключение регистрируется в `peers`: сохраняется `{ session, online, state: "active", timestamp, send() }`. При закрытии соединения или пустом сообщении на шлюзе выполняется `deleteSession`, удаляются токены уведомлений и связанные PTY. На стороне шлюза поддерживается keepalive: каждые 1000 мс отправляется `ping`, отсутствие `pong` в течение 2*TIMEOUT приводит к переподключению.
- **Формат сообщений**. Все команды — JSON-объекты c полем `type`. Общие дополнительные поля: `id` (ключ состояния), `payload` (данные), `ref`/`value` (элементы коллекций), `session` (для некоторых ответов Janus/SIP), произвольные поля доменных подсистем. Некорректный JSON приводит к исключению, которое логируется без разрыва соединения.
- **GET запросы через gateway**. GET запросы работают как через локальное подключение (`ws://<host>:3000`), так и через удалённый gateway (`wss://gate.reacthome.net/<mac>`). Формат команды одинаковый:
  ```json
  {"type": "get", "state": ["device-uuid"]}
  ```
  Ответ приходит в виде серии сообщений `ACTION_SET` с данными запрошенных объектов.
- **Команды состояния**. `ACTION_SET`, `ACTION_ADD`, `ACTION_DEL`, `ACTION_MAKE_BIND`, `ACTION_ADD_BIND` вызывают одноимённые операции `src/actions`. `ACTION_SET` c `id !== "pool"` изменяет записи в памяти; когда поле `payload` содержит сценарий (`title`, `code`), триггерится отложенная инициализация ассистента. Команда `ACTION_ASSIST` обрабатывается синхронно: ответ ассистента отправляется в тот же сокет методом `peer.send()`.
- **Управление активами**. `ACTION_ASSET` принимает `name` и `payload` (base64). После записи файла в `var/assets` отправляется `broadcast({ type: LIST, assets: [name] })`, информируя остальных клиентов.
- **Инициализация клиентов**. `LIST` возвращает снимок состояния и список ассетов текущего демона. Пример ответа:
  ```json
  {"type":"list","state":[["01:23:45:67:89:ab",1684320000000]],"assets":["wall.png"]}
  ```
  Команда `GET` позволяет запросить конкретные сущности:  
  ```json
  {"type":"get","state":["project/main"],"assets":["wall.png"]}
  ```
  Ответ формируется серией сообщений `ACTION_SET` и `ACTION_ASSET`.
- **Push и сессии**. Сообщение `{"type":"token","token":"<apns|fcm>","platform":"ios"}` регистрирует push-токен и привязывает его к текущему `session`. При закрытии соединения токен удаляется через `deleteSession`.
- **Домены медиа и камер**. SIP-команды (`ACK`, `BYE`, `INFO`) маршрутизируются либо в обработчики звонков (`onAck`, `onBye`, `onInfo`), либо ретранслируются другими клиентам через `broadcast`. Камерные события `WATCH`, `START`, `STOP`, `PAUSE` делегируются в `src/camera`. Janus использует `KEEPALIVE` (для поддержания сессии) и `CANDIDATE` (ICE-триклинг).
- **Терминал**. `PTY`-сообщения имеют вид `{"type":"pty","chunk":"ls\n","rows":24,"cols":80}`. Соединение открывает или переиспользует `node-pty`; вывод передаётся обратно как `{"type":"pty","chunk":"output"}`.
- **Навигация и состояние UI**. Дополнительные типы `navigate` и `state` синхронизируют интерфейс: `navigate` рассылается всем пользователям, `state` обновляет поле `peer.state` и не транслируется.
- **Делегирование в сервисы**. Любой неизвестный `type` передаётся в `service.run(action)`, что позволяет вызывать команды устройств (`ACTION_DO`, `ACTION_SCRIPT_RUN`, расписания). Таким образом, вебсокет служит унифицированным API для управления оборудованием и инфраструктурой.
- **Примеры полезной нагрузки**.
  ```json
  {"type":"ACTION_SET","id":"living-room/light","payload":{"value":1}}
  ```
  ```json
  {"type":"ACTION_SCRIPT_RUN","id":"scene/party"}
  ```
  ```json
  {"type":"ACTION_ASSET","name":"plan.png","payload":"<base64>"}
  ```
- **Формат через шлюз**. ⚠️ **ВАЖНО:** Внешние клиенты отправляют **чистый JSON без префиксов**. Gateway сервер сам добавляет session ID (36 символов UUID) при маршрутизации к демону. Клиент отправляет:
  ```json
  {"type":"ACTION_SET","id":"device/relay/1","payload":{"value":1}}
  ```
  Gateway автоматически добавляет session ID: `{session_id}{json_message}`. При получении ответов от gateway клиент должен удалить первые 36 символов (session ID) перед парсингом JSON.
- **Рассылка событий**. Все события от устройств, SIP/Janus, обновления состояний и результаты операций передаются через `broadcast` или `send`. Это обеспечивает консистентный real-time поток для UI, пуш-шлюзов и терминалов.

## Структура каталогов
```
src/
  actions/          # операции над состоянием, биндинги, учет устройств
  assets/           # управление файловыми ресурсами var/*
  assist/           # обработка текстовых команд, утилиты сопоставления
  camera/, janus/, sip/  # видеозвонки и медиа-потоки
  controllers/      # бизнес-логика (device, service, state, cpu, weather)
  drivers/          # интеграция с оборудованием и протоколами
  notification/     # push, токены, сервисы уведомлений
  rbus/             # реализация шины RBUS (serial и UDP адаптеры)
  sockets/          # транспорт событий для устройств
  terminal/, websocket/  # терминал и WebSocket коммуникации
  util.js и др.     # вспомогательные функции (UUID, CRC, SDP)
```

## Требования и окружение
- Node.js 18+ (не ниже LTS, для корректной работы `better-sqlite3`, `level`, `node-pty`).
- npm 8+.
- Доступ к сетевым портам: UDP 2016–2021, WebSocket 3000, протоколы устройств (серийные порты `/dev/tty*`, TCP драйверов).
- Внешние сервисы (опционально):
  - Apple Push Notification (`src/notification/apn.js`);
  - Firebase Admin SDK (`src/notification/firebase.js`);
  - Janus и SIP-серверы, описанные в `src/janus` и `src/sip`.

## Подготовка окружения
1. Создайте директорию `var` рядом с репозиторием (или позвольте демону сделать это автоматически).
2. Установите зависимости:
   ```
   npm install
   ```
3. При необходимости подготовьте конфигурацию устройств в LevelDB (`var/db`) или импортируйте существующий дамп.

## Запуск
Для локального запуска:
```
node daemon.js
```
Демон автоматически:
- инициализирует директории `var/assets`, `var/tmp`, `var/db`;
- восстанавливает состояние устройства по MAC-адресу;
- запускает discovery, WebSocket, Janus, SIP, драйверы и контроллеры.

## Конфигурация
- Состояние проекта хранится по ключам вида `<mac>/<сущность>` в LevelDB.
- Справочники устройств и протоколов настроены через `src/constants.js`.
- Настройки Janus, SIP, уведомлений и ассистента находятся в соответствующих каталогах и зависят от развертывания.
- Дополнительные параметры (например, IP-пулы, порты) можно править в `src/constants.js`.

## Диагностика и сопровождение
- Логи пишутся в stdout/stderr; перенаправьте вывод в файлы при работе как сервис.
- Для обслуживания RBUS доступен утилитарный запуск `node rbus.js`, который открывает последовательный порт и привязывает его к UDP-шине.
- Чистка устаревшего состояния реализована в `src/gc.js`; функция `cleanup` пока закомментирована.
- Терминальный доступ и shell-скрипты управляются через контроллер сервисов (`ACTION_SHELL_START`/`STOP`).

## Рекомендации по разработке
- Соблюдайте доменное разделение: действия (`src/actions`) не должны напрямую обращаться к транспортам, взаимодействие идет через контроллеры и драйверы.
- Для новых устройств создавайте адаптеры в `src/drivers/<vendor>` и регистрируйте их в `src/drivers/driver.js`.
- Тесты можно добавлять в `src/assist/test.js` по аналогии; интеграционные сценарии оформляйте в отдельные скрипты.
- При изменении протоколов обновляйте `src/constants.js` и поддерживайте обратную совместимость через проверки версий устройств.

## Полезные команды
- `npm install` — установка зависимостей.
- `node daemon.js` — запуск основного демона.
- `node rbus.js` — тестовый мост RBUS ↔ UDP (требует настройки интерфейсов).
