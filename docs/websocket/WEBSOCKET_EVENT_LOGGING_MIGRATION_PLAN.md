## Цель

Переход на отдельный сервис `event-logger` без изменения формата событий в OpenSearch. Сервис будет подключаться к демону через WebSocket (`ws://localhost:3000`) и логировать события в OpenSearch.

### Цели миграции

Основная цель миграции — обеспечить надёжную основу для аналитики и мониторинга системы умного дома через выделение логирования в отдельный сервис.

#### 1. Климатический мониторинг

- **Непрерывный сбор данных** о температуре, влажности, CO₂ для анализа климатических условий
- **Отслеживание работы климатического оборудования** (кондиционеры, вентиляторы, тёплые полы)
- **Анализ эффективности** систем климат-контроля и выявление аномалий
- **Исторические данные** для прогнозирования и оптимизации энергопотребления

#### 2. Анализ работы потребителей энергии

**Ключевой механизм:** Кэширование состояния актуаторов для отслеживания времени включения и расчёта длительности работы.

- **Кэширование состояния актуаторов:** При включении сохраняется время включения (`onTimestamp`) в кэш `actuatorStateCache`
- **Мониторинг времени работы** актуаторов (лампы, вентиляторы, кондиционеры, тёплые полы)
- **Расчёт длительности работы** устройств при выключении (`duration = now - onTimestamp`) для анализа энергопотребления
- **Выявление паттернов использования** оборудования на основе данных о времени работы
- **Оптимизация энергопотребления** на основе данных о реальной работе устройств
- **Отслеживание выключений** с информацией о длительности работы (поле `extra.actuator_off`):
  - Время последнего включения (`on_timestamp`)
  - Длительность работы в миллисекундах и секундах
  - Параметр и значение при включении

#### 3. Анализ цепочек вызовов и трассировка

**Ключевой механизм:** Генерация и кэширование `trace_id` для построения полных цепочек связности событий.

- **Трассировка событий** через поле `trace_id` для построения полных цепочек связности
- **Отслеживание причинно-следственных связей** между событиями (триггеры, скрипты, устройства)
- **Анализ работы автоматизаций** — какие скрипты запускаются, от чего и с какими последствиями
- **Диагностика проблем** через построение полной цепочки событий от триггера до результата
- **Оптимизация автоматизаций** на основе анализа реальных цепочек выполнения

**Алгоритм работы трассировки:**

1. **Инициализация цепочки (событие без триггера):**
   - Событие с `trigger.type === 'unknown'` или без триггера
   - Генерируется новый `trace_id` через `uuid.v4()`
   - `trace_id` сохраняется в кэш `traceIdCache` по ID события/устройства
   - Это событие становится началом цепочки

2. **Продолжение цепочки (событие с триггером):**
   - Событие с триггером (script, schedule, device, timer)
   - Ищется `trace_id` в кэше по `context.ref` (ID триггера)
   - Если найден — используется существующий `trace_id` (связывание с предыдущим событием)
   - Если не найден — генерируется новый `trace_id` и сохраняется для обоих ID
   - `trace_id` сохраняется в кэш по ID текущего события для последующих связей

3. **Связывание цепочек:**
   - Все связанные события имеют один и тот же `trace_id`
   - Цепочка начинается с события без триггера и продолжается через события с триггерами
   - События скриптов (`executed`/`last_execution`) связываются с событиями устройств через `trace_id`

**Пример работы алгоритма:**

```
Событие 1: Устройство включилось (trigger.type = 'unknown')
  → Генерируется trace_id = "abc-123"
  → Сохраняется в кэш: device_id → "abc-123"

Событие 2: Скрипт запустился (trigger.type = 'script', ref = device_id)
  → Ищется trace_id в кэше по device_id
  → Найден: "abc-123"
  → Используется "abc-123" для события скрипта
  → Сохраняется в кэш: script_id → "abc-123"

Событие 3: Устройство изменилось от скрипта (trigger.type = 'script', ref = script_id)
  → Ищется trace_id в кэше по script_id
  → Найден: "abc-123"
  → Используется "abc-123" для события устройства
  → Все три события имеют один trace_id = "abc-123"
```

**Структура данных:**
- Кэш: `traceIdCache` (Map: `id -> trace_id`)
- Ключ кэша: ID устройства, скрипта или события
- Значение кэша: UUID `trace_id` для связывания цепочек

#### Поддержка нескольких умных домов (проектов)

**Важно:** Система поддерживает несколько умных домов (проектов) в рамках одного OpenSearch кластера.

**Механизм разделения:**

1. **Поле `project` в событиях:**
   - Каждое событие содержит поле `project` (например, `"pochta"`, `"mindal"`)
   - Поле заполняется автоматически через `getProjectName(id)` из иерархии устройств
   - По умолчанию используется `"pochta"` (если проект не найден)
   - **Важно:** Поле `project` **всегда присутствует** в событии (не может быть `null`)

2. **Единый индекс для всех проектов:**
   - Все проекты пишутся в один индекс: `reacthome-events-YYYY-MM-DD`
   - Разделение происходит через фильтрацию по полю `project` в запросах
   - Это позволяет:
     - Сравнивать данные между проектами
     - Использовать единые дашборды с фильтрацией
     - Централизованное управление индексами

3. **Несколько серверов (Raspberry Pi):**
   - Каждый сервер может иметь свой проект
   - Все серверы пишут в один OpenSearch кластер
   - События автоматически помечаются полем `project` при логировании

**Примеры запросов с фильтрацией по проекту:**

```json
{
  "query": {
    "bool": {
      "must": [
        { "term": { "project": "pochta" } },
        { "range": { "timestamp": { "gte": "now-24h" } } }
      ]
    }
  }
}
```

**Конфигурация для разных проектов:**

- **Один сервер, один проект:** Используется автоматическое определение проекта из иерархии
- **Один сервер, несколько проектов:** Поддерживается через поле `project` в событиях
- **Несколько серверов, разные проекты:** Каждый сервер логирует в один кластер, разделение через `project`

**Важно:** Если требуется полное разделение проектов (отдельные индексы), можно использовать `OPENSEARCH_INDEX_PREFIX` с именем проекта:
- `reacthome-events-pochta-YYYY-MM-DD`
- `reacthome-events-mindal-YYYY-MM-DD`

Но по умолчанию используется единый индекс с полем `project` для упрощения управления.

#### Технические преимущества

- **Независимость сервиса** — перезапуск event-logger не влияет на работу демона
- **Масштабируемость** — возможность запуска нескольких экземпляров для резервирования
- **Оптимизация ресурсов** — снижение нагрузки на основной демон (важно для Raspberry Pi)
- **Гибкость развёртывания** — возможность размещения на отдельном сервере
- **Поддержка нескольких проектов** — автоматическое разделение через поле `project` в событиях

### Ограничения и требования

- **Формат событий:** Должен оставаться идентичным текущему формату для сохранения совместимости с существующими дашбордами и запросами
- **Производительность:** Не должно быть деградации производительности основного демона
- **Надёжность:** Гарантия отсутствия потери событий при миграции — критично для непрерывности аналитики
- **Обратная совместимость:** Возможность отката к встроенному логированию при необходимости
- **Непрерывность данных:** Обеспечение непрерывного сбора данных для климатического мониторинга и анализа
- **Поддержка нескольких проектов:** Поле `project` в событиях должно корректно заполняться для разделения данных разных умных домов

## Архитектура решения

### Базовая архитектура (один сервер)

```
Демон (daemon.js)
    ↓ ACTION_SET с _context
WebSocket (ws://localhost:3000)
    ↓
Event Logger (event-logger.js)
    ↓ обработка, фильтрация, создание событий
OpenSearch (reacthome-events-YYYY-MM-DD)
    ↓ поле project в каждом событии
```

### Архитектура для нескольких умных домов

```
Сервер 1 (Raspberry Pi - pochta)
    Демон → WebSocket → Event Logger → OpenSearch
    ↓
    События с project="pochta"

Сервер 2 (Raspberry Pi - mindal)
    Демон → WebSocket → Event Logger → OpenSearch
    ↓
    События с project="mindal"

OpenSearch (reacthome-events-YYYY-MM-DD)
    ├─ События project="pochta"
    └─ События project="mindal"
    
    Разделение через фильтрацию по полю project
```

**Важно:**
- Все серверы пишут в один OpenSearch кластер
- Разделение происходит через поле `project` в событиях
- Каждый сервер автоматически определяет свой проект из иерархии устройств
- Запросы к OpenSearch фильтруются по `project` для получения данных конкретного умного дома

## Формат события в OpenSearch

### Полная структура события

Каждое событие, отправляемое в OpenSearch, имеет следующую структуру:

```json
{
  "timestamp": 1763314232510,
  "id": "40:64:06:c0:5d:b5/do/1",
  "device": {
    "type": "DEVICE_TYPE_RELAY_2",
    "human": "Свет Лоджия",
    "name": "Свет Лоджия"
  },
  "param": "value",
  "old": 0,
  "new": 1,
  "value": {
    "old": 0.0,
    "new": 1.0
  },
  "trigger": {
    "type": "script",
    "ref": "002b333c-f189-4c3a-9f36-0a7f6f1d48d3",
    "id": "90:89:d3:f1:2d:0f",
    "human": "Датчик движения / Скрипт включения света",
    "session": null,
    "remote_ip": null
  },
  "site": "Лоджия",
  "project": "pochta",
  "trace_id": "a5b0a8f3-fe41-4235-b602-3a09e1eeddbb",
  "extra": {
    "actuator_off": {
      "on_timestamp": 1763314000000,
      "duration_ms": 232510,
      "duration_seconds": 233,
      "param": "value",
      "value": 1
    }
  }
}
```

### Описание полей

| Поле | Тип | Обязательное | Описание |
|------|-----|--------------|----------|
| `timestamp` | number | ✅ Да | Unix timestamp в миллисекундах (время создания события) |
| `id` | string | ✅ Да | Идентификатор устройства/канала/скрипта |
| `device.type` | string \| null | ✅ Да | Тип устройства (например, "DEVICE_TYPE_RELAY_2") |
| `device.human` | string \| null | ✅ Да | Человекочитаемое название устройства (title/code/name через "/") |
| `device.name` | string \| null | ✅ Да | Поле name устройства (если есть) |
| `param` | string | ✅ Да | Имя изменённого параметра (value, brightness, r, g, b, fan_speed, mode, direction, setpoint, temperature, humidity, co2, executed, last_execution) |
| `old` | any \| null | ✅ Да | Предыдущее значение параметра (может быть null для первого значения) |
| `new` | any | ✅ Да | Новое значение параметра |
| `value` | object | ⚠️ Опционально | Только для числовых параметров (определяется через `isNumericParam()`). Содержит `{ old, new }` с округлёнными до десятых значениями |
| `trigger.type` | string | ✅ Да | Тип триггера (websocket, script, schedule, device, timer, unknown) |
| `trigger.ref` | string \| null | ✅ Да | ID скрипта/расписания/таймера, который вызвал изменение |
| `trigger.id` | string \| null | ✅ Да | ID устройства-источника (для скриптов, вызванных устройствами) |
| `trigger.human` | string \| null | ✅ Да | Человекочитаемое название триггера (title/code/name через "/") |
| `trigger.session` | string \| null | ✅ Да | ID WebSocket сессии (для команд через WebSocket) |
| `trigger.remote_ip` | string \| null | ✅ Да | IP адрес клиента (для команд через WebSocket) |
| `site` | string \| null | ✅ Да | Название локации (Site) или проекта (Project, например "pochta", "mindal") |
| `project` | string | ✅ Да | Название проекта (например, "pochta") - **всегда присутствует** (не может быть null, по умолчанию "pochta") |
| `trace_id` | string | ⚠️ Опционально | UUID для трассировки цепочек событий (только в event-logger, на верхнем уровне события) |
| `extra` | object | ✅ Да | Дополнительные метаданные (всегда присутствует, может быть пустым объектом `{}`) |
| `extra.actuator_off` | object | ⚠️ Опционально | Информация о выключении актуатора (только при выключении актуаторов, внутри `extra`) |

### Опциональные поля

**Поле `value`:**
- Присутствует **только для числовых параметров** (определяется через `isNumericParam(param)`)
- Для нечисловых параметров поле `value` **не должно присутствовать** в событии
- Содержит округлённые до десятых значения: `{ old: 0.0, new: 1.0 }`

**Поле `trace_id`:**
- Присутствует **только в event-logger** (для трассировки цепочек событий)
- Находится на **верхнем уровне события** (не в `extra`)
- Генерируется через `uuid.v4()` для связывания связанных событий

**Поле `extra.actuator_off`:**
- Присутствует **только при выключении актуаторов** (когда `new < old` для актуаторов)
- Содержит информацию о времени включения и длительности работы:
  - `on_timestamp` — время последнего включения (Unix timestamp в миллисекундах)
  - `duration_ms` — длительность работы в миллисекундах
  - `duration_seconds` — длительность работы в секундах (округлённое)
  - `param` — параметр, который контролировал включение
  - `value` — значение параметра при включении

    "old": 0.0,
    "new": 1.0

```

**Событие с нечисловым параметром (без поля `value`):**
```json

  "old": null,
  "new": true,

       return traceId; // Связываем с предыдущим событием

## Критические моменты и узкие места

1. **Идентичность формата:** Использовать экспортированные функции из `event-log.js`

   - **Узкое место:** Не все функции были в первоначальном списке экспортов (добавлены `getTriggerDeviceId`, `isNumericParam`, `NUMERIC_PARAMS`)

2. **Непрерывность:** Параллельная работа минимум 3-7 дней перед переключением

3. **Обратная совместимость:** Поле `_context` опциональное, флаг `EVENT_LOGGING_ENABLED` по умолчанию `true`

4. **План отката:** Включить встроенное логирование при проблемах

5. **Тест совместимости:** Критический тест должен проходить успешно перед переключением

6. **События executed/last_execution (критично):**

   - Эти события обрабатываются специально в `event-log.js` (строки 670-723)
   - Должны логироваться всегда, минуя обычную фильтрацию
   - Event-logger должен воспроизвести эту логику
   - **Узкое место:** Если не обработать специально, события могут быть пропущены

7. **trigger.id и trigger.human (критично):**

   - Определяются через `getTriggerDeviceId(context)` и `getTriggerHuman(context, triggerId)`
   - `deviceId` должен быть в `_context` из `ACTION_SET`
   - **Узкое место:** Если `deviceId` не передан в `_context`, `trigger.id` будет `null`, и `trigger.human` покажет название скрипта вместо устройства-источника
   - **Решение:** Добавить `deviceId` в `_context` при broadcast в `src/actions/create.js` ✅

8. **Поле value для числовых параметров:**

   - Добавляется только для числовых параметров (определяется через `isNumericParam`)
   - **Узкое место:** Если не проверить `isNumericParam`, поле `value` может отсутствовать или быть лишним

9. **Обработка changedPayload:**

   - Логировать только параметры из `payload`, а не все поля из `state`
   - **Узкое место:** Если логировать все поля из `state`, будут ложные срабатывания (old === new для не изменённых полей)

10. **Сопоставление событий в тесте:**

    - События должны сопоставляться по `id + timestamp + param`
    - Допускается разница в timestamp до 5 секунд (задержка WebSocket)
    - **Узкое место:** Если сопоставлять только по `id + timestamp`, могут быть ложные совпадения

11. **Новые поля в событиях event-logger:**
    - `trace_id` — опциональное поле для трассировки цепочек событий (может отсутствовать в старых событиях)
    - `extra.actuator_off` — опциональное поле с информацией о выключении актуатора (только при выключении)
    - Эти поля не должны влиять на сравнение формата, так как они являются расширением функциональности

12. **Кеширование siteName:**

    - В `event-log.js` используется кеш с TTL 1 минута
    - Event-logger может использовать тот же кеш или свой (не критично для идентичности формата)

13. **События от скриптов:**

    - События `executed`/`last_execution` логируются через `set()` в `service.js`, который вызывает `apply()`
    - Это значит, что они ДОЛЖНЫ проходить через `ACTION_SET` и event-logger их получит
    - **Проверка:** Убедиться, что события `executed`/`last_execution` действительно приходят через `ACTION_SET`

14. **Критическое исправление setTimeout в ACTION_SCRIPT_RUN:**

    - **Проблема:** AsyncLocalStorage не покрывает `setTimeout` с delay, контекст теряется
    - **Решение:** Явная передача контекста через замыкание и `contextStore.run()` в callback

### Детали реализации встроенного логирования

#### Архитектура встроенного логирования

Встроенное логирование работает следующим образом:

1. **Контекст создаётся в точках входа:**
   - WebSocket: `src/websocket/handle.js` - обёртка в `contextStore.run()` с типом 'websocket'
   - Устройства: `src/controllers/device.js` - обёртка `handleData` в `contextStore.run()` с типом 'device'
   - Скрипты: `src/controllers/service.js` - обёртка выполнения скрипта в `contextStore.run()` с типом 'script'
   - Расписания: `src/controllers/service.js` - контекст создаётся при создании CronJob и восстанавливается в callback

2. **Контекст передаётся через AsyncLocalStorage:**
   - `src/logging/context.js` - AsyncLocalStorage хранилище
   - Контекст доступен во всех асинхронных операциях в рамках одного запроса/действия

3. **Логирование в `src/actions/create.js`:**
   - Функция `apply()` получает контекст через `contextStore.getStore()`
   - Создаётся глубокая копия `oldState` для предотвращения мутации
   - Вызывается `eventLog.add()` с передачей `cleanPayload` (только изменённые параметры)

4. **Обработка в `src/logging/event-log.js`:**
   - Фильтрация через `filters.shouldLogEvent()`
   - Специальная обработка событий `executed`/`last_execution` (строки 670-723)
   - Батчинг событий (50 событий, 500ms таймер)
   - Отправка в OpenSearch через `opensearch.sendBatch()`

#### Критические моменты реализации

1. **Глубокое копирование oldState:**
   - `state.get()` возвращает ссылку на объект
   - Без копирования `oldState` и `newState` будут указывать на один объект после `state.set()`
   - Решение: `JSON.parse(JSON.stringify(oldStateRaw))`

2. **Передача cleanPayload:**
   - `state.set()` делает merge через `Object.assign`
   - Для параметров, не переданных в `payload`, `old` и `new` будут одинаковыми
   - Решение: передавать только параметры из `payload` (без `timestamp`)

3. **Сохранение контекста в setTimeout:**
   - AsyncLocalStorage не покрывает `setTimeout` с delay
   - Решение: явная передача контекста через замыкание и `contextStore.run()`

4. **Сохранение контекста в CronJob:**
   - Контекст теряется при выполнении callback
   - Решение: сохранить контекст при создании CronJob и восстановить в callback

### Связь с event-logger

**Важно:** Встроенное логирование и event-logger используют одни и те же модули:
- `src/logging/event-log.js` - функции форматирования событий (экспортируемые)
- `src/logging/filters.js` - фильтры для определения, какие события логировать
- `src/logging/opensearch.js` - модуль отправки событий в OpenSearch

**Различия:**
- Встроенное логирование: события логируются напрямую в `src/actions/create.js`
- Event-logger: события получаются через WebSocket (`ACTION_SET` с `_context`) и логируются отдельным сервисом

**Преимущества event-logger:**
- Независимость от демона (перезапуск не влияет на логирование)
- Масштабируемость (несколько экземпляров для резервирования)
- Оптимизация ресурсов (снижение нагрузки на демон)
