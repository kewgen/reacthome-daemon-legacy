# Monitor.js - Инструмент мониторинга устройств

Интерактивный терминальный UI для мониторинга и отладки щитовых устройств в реальном времени.

## 🚀 Быстрый старт

```bash
# Установка зависимостей (если ещё не установлены)
npm install terminal-kit ws

# Запуск на локальной машине (подключение к localhost:3000)
node src/monitor.js

# Запуск с подключением к удалённому серверу
REACTHOME_WS_URI=ws://192.168.1.100:3000 node src/monitor.js

# Запуск с включенным логированием WebSocket
WS_REQUEST_LOGGING=1 node src/monitor.js
```

## 📋 Возможности

### Интерфейс
- **Три панели:** фильтры / таблица устройств / детали устройства
- **Фильтрация:** по типам устройств и помещениям
- **Поиск:** быстрый поиск по имени/коду устройства
- **Автообновление:** состояние устройств обновляется в реальном времени

### Отображение
- ✅ Щитовые устройства (актуаторы, сенсоры, контроллеры)
- ✅ Конечные устройства (Smart TOP, Smart BOTTOM)
- ✅ Каналы (do/dim/di/ai) с их состояниями
- ✅ Bind связи между каналами и устройствами
- ✅ Датчики протечки с их статусом
- ✅ Помещения и локации

### Специальные функции
- 💧 Модули датчиков протечки (M1, тип 0xab/171)
- 🔗 Отображение bind связей для каналов
- 📊 Статистика устройств по типам
- 📋 Копирование данных в буфер обмена

## ⌨️ Управление

| Клавиша | Действие |
|---------|----------|
| `Tab` | Переключение между панелями (фильтры / таблица / детали) |
| `↑` / `↓` | Навигация по списку |
| `j` / `k` | Навигация по списку (vi-style) |
| `Enter` | Выбор фильтра / Показать детали устройства |
| `c` | Копировать содержимое раздела "Устройство" в буфер обмена |
| `y` + `c` | Копировать строку таблицы в буфер обмена |
| `q` | Выход |
| `Ctrl+C` | Выход |

## 🔧 Переменные окружения

### REACTHOME_WS_URI
URI WebSocket сервера для подключения.

```bash
# По умолчанию
REACTHOME_WS_URI=ws://localhost:3000

# Для удалённого сервера
REACTHOME_WS_URI=ws://192.168.1.100:3000
```

### WS_REQUEST_LOGGING
Включение детального логирования WebSocket запросов и ответов.

```bash
# Включить логирование
WS_REQUEST_LOGGING=1 node src/monitor.js

# Логи будут записаны в:
# - logs/monitor/ws-in.log  (входящие сообщения)
# - logs/monitor/ws-out.log (исходящие запросы)
```

### WS_LOG_DIR
Директория для логов WebSocket (по умолчанию: `logs/monitor/`).

```bash
WS_LOG_DIR=/custom/path/to/logs WS_REQUEST_LOGGING=1 node src/monitor.js
```

## 📊 Примеры использования

### 1. Мониторинг локальной системы
```bash
node src/monitor.js
```

### 2. Удалённый мониторинг с логированием
```bash
WS_REQUEST_LOGGING=1 REACTHOME_WS_URI=ws://192.168.1.100:3000 node src/monitor.js
```

### 3. Анализ производительности WebSocket
```bash
# Включить логирование и посмотреть статистику
WS_REQUEST_LOGGING=1 node src/monitor.js

# В другом терминале анализировать логи:
tail -f logs/ws-in.log   # Входящие сообщения
tail -f logs/ws-out.log  # Исходящие запросы

# Статистика:
cat logs/ws-in.log | grep "ACTION_SET" | wc -l   # Количество ACTION_SET
cat logs/ws-out.log | grep "GET запрос" | wc -l  # Количество GET запросов
```

## 🏗️ Архитектура

### Загрузка данных
```
1. Подключение к WebSocket (ws://localhost:3000)
   ↓
2. LIST запрос → получение списка ID устройств
   ↓
3. GET запрос → получение полных данных для всех устройств
   ↓
4. Обработка и фильтрация устройств
   ↓
5. Построение UI с тремя панелями
   ↓
6. Real-time обновления через ACTION_SET сообщения
```

### Обработка устройств
- **Помещения** (site/project): загружаются только через WebSocket
- **Щитовые устройства**: фильтруются по типам (актуаторы/сенсоры/контроллеры)
- **Конечные устройства**: Smart TOP/BOTTOM и другие
- **Каналы**: автоматически связываются с родительскими устройствами
- **Потребители**: загружаются из массивов помещений

## 🐛 Отладка

### Проблема: Monitor не подключается к WebSocket
```bash
# ВАЖНО: НЕ ЗАПУСКАТЬ ЛОКАЛЬНЫЙ DAEMON
pm2 list

# Вместо этого убедитесь, что основной демон доступен по WebSocket:
#   REACTHOME_WS_URI=ws://<ip-основного-демона>:3000 node src/monitor.js
# и/или проверьте сеть/порт 3000 на стороне основного демона.

# Проверить порт:
netstat -an | grep 3000
```

### Проблема: Не видны некоторые устройства
```bash
# Включить логирование WebSocket:
WS_REQUEST_LOGGING=1 node src/monitor.js

# Проверить, что устройства приходят в GET ответах:
grep "ACTION_SET" logs/ws-in.log | grep "device-id"
```

### Проблема: Таймаут подключения
```bash
# Увеличить таймаут (в коде monitor.js):
const STATE_REQUEST_TIMEOUT = 30000; # было 10000
```

## 📝 Известные особенности

1. **Каналы не отображаются как отдельные устройства** - это правильно, они отображаются внутри родительских устройств

2. **Помещения могут показывать "не зарезолвлено"** - это означает, что помещение упоминается в устройстве, но не найдено как отдельный объект

3. **Некоторые устройства могут не иметь site** - для актуаторов применяется статистический резолв через каналы

4. **Модули датчиков протечки (M1)** требуют специальной обработки bind связей

## ⚠️ Требования

- Node.js 18+ (на Raspberry Pi v20.19.2+)
- npm 8+
- Доступный основной демон с WebSocket сервером на порту 3000 (локальный daemon из этого репозитория НЕ нужен)

## 🎯 Использование в production

Monitor.js - это **инструмент для отладки и мониторинга**, не для production использования.

Для production используйте:
- `event-logger.js` - логирование событий в OpenSearch
- PM2 для мониторинга процессов
- Grafana для визуализации метрик

## 💡 Советы

1. **Для быстрого поиска устройства:** используйте фильтры по типам и помещениям

2. **Для копирования данных:** используйте `c` (копировать всё) или `y+c` (копировать строку)

3. **Для анализа производительности:** включайте `WS_REQUEST_LOGGING=1`

4. **Для отладки bind связей:** смотрите раздел "Каналы" в деталях устройства

5. **Для анализа датчиков протечки:** выберите модуль M1 и посмотрите список всех датчиков
