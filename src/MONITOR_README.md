# Monitor.js - Инструмент мониторинга устройств

Интерактивный терминальный UI для мониторинга и отладки щитовых устройств в реальном времени.

## 🚀 Быстрый старт

```bash
# Установка зависимостей (если ещё не установлены)
npm install terminal-kit ws

# Запуск на локальной машине (подключение к localhost:3000)
node src/monitor.js

# Запуск с подключением к удалённому серверу
REACTHOME_WS_URI=ws://192.168.1.100:3000 node src/monitor.js

# Запуск с включенным логированием WebSocket
WS_REQUEST_LOGGING=1 node src/monitor.js
```

## 📋 Возможности

### Интерфейс
- **Три панели:** фильтры / таблица устройств / детали устройства
- **Фильтрация:** по типам устройств и помещениям
- **Поиск:** быстрый поиск по имени/коду устройства
- **Автообновление:** состояние устройств обновляется в реальном времени

### Отображение
- ✅ Щитовые устройства (актуаторы, сенсоры, контроллеры)
- ✅ Конечные устройства (Smart TOP, Smart BOTTOM)
- ✅ Каналы (do/dim/di/ai) с их состояниями
- ✅ Bind связи между каналами и устройствами
- ✅ Датчики протечки с их статусом
- ✅ Помещения и локации

### Специальные функции
- 💧 Модули датчиков протечки (M1, тип 0xab/171)
- 🔗 Отображение bind связей для каналов
- 📊 Статистика устройств по типам
- 📋 Копирование данных в буфер обмена

## 🔧 Переменные окружения

### REACTHOME_WS_URI
URI WebSocket сервера для подключения.

```bash
# По умолчанию
REACTHOME_WS_URI=ws://localhost:3000

# Для удалённого сервера
REACTHOME_WS_URI=ws://192.168.1.100:3000
```

### WS_REQUEST_LOGGING
Включение детального логирования WebSocket запросов и ответов.

```bash
# Включить логирование
WS_REQUEST_LOGGING=1 node src/monitor.js

# Логи будут записаны в:
# - logs/ws-in.log  (входящие сообщения)
# - logs/ws-out.log (исходящие запросы)
```

### WS_LOG_DIR
Директория для логов WebSocket (по умолчанию: `logs/`).

```bash
WS_LOG_DIR=/custom/path/to/logs WS_REQUEST_LOGGING=1 node src/monitor.js
```

## 🏗️ Архитектура

### Загрузка данных
```
1. Подключение к WebSocket (ws://localhost:3000)
   ↓
2. LIST запрос → получение списка ID устройств
   ↓
3. GET запрос → получение полных данных для всех устройств
   ↓
4. Обработка и фильтрация устройств
   ↓
5. Построение UI с тремя панелями
   ↓
6. Real-time обновления через ACTION_SET сообщения
```

### Обработка устройств
- **Помещения** (site/project): загружаются только через WebSocket
- **Щитовые устройства**: фильтруются по типам (актуаторы/сенсоры/контроллеры)
- **Конечные устройства**: Smart TOP/BOTTOM и другие
- **Каналы**: автоматически связываются с родительскими устройствами
- **Потребители**: загружаются из массивов помещений

## 🐛 Отладка

### Проблема: Monitor не подключается к WebSocket
```bash
# Проверить, что daemon запущен:
pm2 list

# Проверить логи daemon:
pm2 logs daemon

# Проверить порт:
netstat -an | grep 3000
```

### Проблема: Не видны некоторые устройства
```bash
# Включить логирование WebSocket:
WS_REQUEST_LOGGING=1 node src/monitor.js

# Проверить, что устройства приходят в GET ответах:
grep "ACTION_SET" logs/ws-in.log | grep "device-id"
```

### Проблема: Таймаут подключения
```bash
# Увеличить таймаут (в коде monitor.js):
const STATE_REQUEST_TIMEOUT = 30000; # было 10000
```

## 📝 Известные особенности

1. **Каналы не отображаются как отдельные устройства** - это правильно, они отображаются внутри родительских устройств

2. **Помещения могут показывать "не зарезолвлено"** - это означает, что помещение упоминается в устройстве, но не найдено как отдельный объект

3. **Некоторые устройства могут не иметь site** - для актуаторов применяется статистический резолв через каналы

4. **Модули датчиков протечки (M1)** требуют специальной обработки bind связей

## 🔍 Алгоритмы резолвинга связей

Монитор использует несколько алгоритмов для резолвинга связей между устройствами. Это позволяет отображать полную информацию о связях в обоих направлениях.

### 1. Двунаправленный резолв привязок потребителей к актуаторам

**Проблема:** Привязка может храниться в двух направлениях:
- У потребителя: `bind = "54:10:ec:19:c4:e8/do/11"` (путь к каналу актуатора)
- У канала актуатора: `bind = "1853560d-089f-4df7-ac2f-9043f62dcffd"` (ID потребителя)

**Алгоритм:**

```
Для каждого канала актуатора (DO/DIM/AO):
  1. Метод 1 (прямой): Проверяем bind в состоянии канала
     - Если bind содержит UUID устройства → ищем устройство по ID
     - Если найдено → linkedDevice = устройство
  
  2. Метод 2 (обратный): Ищем устройства, у которых bind указывает на этот канал
     - Для всех устройств проверяем: device.bind === channelId
     - Если найдено → linkedDevice = устройство
  
  3. Результат: linkedDevice содержит связанное устройство (если найдено)
```

**Пример:**
- Fan устройство имеет `bind: "54:10:ec:19:c4:e8/do/11"`
- При просмотре Fan → показывается привязка к R2/DO/11
- При просмотре R2 → показывается привязка DO/11 → Fan

### 2. Резолв групп каналов (group)

**Проблема:** Некоторые устройства (шторы) привязаны к группам каналов, а не к отдельным физическим каналам.

**Алгоритм:**

```
Для устройства типа "group" (например, group/5):
  1. Ищем все устройства, у которых bind указывает на группу
     - Для всех устройств: device.bind === "{actuatorId}/group/{index}"
  
  2. Для каждой найденной группы:
     - Создаём виртуальный канал типа 'group'
     - Добавляем linkedDevice (устройство, привязанное к группе)
  
  3. Группы отображаются в разделе "Actuator channels" как отдельный тип каналов
```

**Пример:**
- Штора имеет `bind: "54:10:ec:19:c4:e8/group/5"`
- При просмотре R2 → показывается GROUP/5 → Штора

### 3. Резолв привязок сенсоров к модулям

**Проблема:** Сенсоры (герконы, датчики протечки) привязаны к модулям через DI каналы.

**Алгоритм:**

```
Для сенсора с bind формата "{moduleId}/di/{номер}":
  1. Парсим bind: [moduleId, 'di', channelIndex] = bind.split('/')
  
  2. Ищем модуль по ID:
     - Проверяем devicesByMac кэш
     - Если не найдено → ищем в allDevices
  
  3. Получаем состояние канала модуля:
     - channelId = bind
     - channelState = deviceStates.get(channelId)?.state
  
  4. Отображаем:
     - Модуль (название, тип)
     - Канал (DI/{номер})
     - Состояние канала
     - Помещение модуля
```

**Пример:**
- Геркон имеет `bind: "68:27:19:e4:48:38/di/14"`
- При просмотре геркона → показывается привязка к модулю M1, канал DI/14

### 4. Резолв параметров NOVA (приточная вентиляция)

**Проблема:** Устройства NOVA имеют специфичные параметры, которые нужно резолвить в читаемый вид.

**Алгоритм:**

```
Для устройства типа NOVA:
  1. Режим работы (mode):
     - 'cool' → 'Охлаждение'
     - 'heat' → 'Обогрев'
     - 'ventilation' → 'Вентиляция'
     - 'stop' → 'Остановлен'
     - 'auto' → 'Автоматический'
  
  2. Состояние (state):
     - 'stop' → 'Остановлен'
     - 'running' → 'Работает'
     - 'cooling' → 'Охлаждение'
     - 'heating' → 'Обогрев'
     - 'ventilating' → 'Вентиляция'
  
  3. Скорость вентилятора:
     - Проверяем state.fan_speed или state.fan_speed_
     - Отображаем числовое значение
  
  4. Уставка температуры:
     - state.setpoint → отображаем с единицами (°C)
  
  5. Синхронизация:
     - state.synced → ✅/⚠️ индикатор
```

### 5. Резолв подключенных устройств для MODBUS

**Проблема:** MODBUS устройства используются как шлюзы, нужно показывать, какие устройства подключены.

**Алгоритм:**

```
Для устройства типа MODBUS:
  1. Ищем все устройства с bind, указывающим на это MODBUS устройство:
     - Формат bind: "{modbusId}/MODBUS/{address}" или "{modbusId}/modbus/{address}"
     - Для всех устройств: device.bind === "{modbusId}/MODBUS/{address}"
  
  2. Для каждого найденного устройства:
     - Парсим адрес на шине Modbus
     - Получаем информацию об устройстве (название, тип, помещение)
     - Получаем состояние устройства (online, ready, value)
  
  3. Сортируем по адресу на шине Modbus
  
  4. Отображаем:
     - Адрес на шине
     - Название, тип, помещение
     - Статус устройства
     - IP адрес MODBUS устройства (если есть)
```

**Пример:**
- Устройство AC имеет `bind: "f698f5c0-0e7c-40f8-ac40-4af4328d5003/MODBUS/1"`
- При просмотре MODBUS устройства → показывается список всех подключенных устройств с их адресами

### 6. Резолв параметров INTESIS_BOX (кондиционеры)

**Проблема:** Устройства INTESIS_BOX имеют числовые параметры режима и направления, которые нужно резолвить.

**Алгоритм:**

```
Для устройства типа INTESIS_BOX:
  1. Режим работы (mode):
     - 0 → 'Выключен'
     - 1 → 'Обогрев'
     - 2 → 'Охлаждение'
     - 3 → 'Автоматический'
     - 4 → 'Вентиляция'
     - 5 → 'Осушение'
  
  2. Направление воздушного потока (direction):
     - 0 → 'Автоматическое'
     - 1 → 'Горизонтальное'
     - 2 → 'Вертикальное'
     - 3 → 'Качание'
     - 4 → 'Фиксированное'
  
  3. Скорость вентилятора (fan_speed):
     - 0 → 'Автоматическая'
     - 1 → 'Низкая'
     - 2 → 'Средняя'
     - 3 → 'Высокая'
     - 4 → 'Максимальная'
  
  4. Уставка температуры:
     - state.setpoint → отображаем с единицами (°C)
  
  5. Привязка к MODBUS:
     - Парсим bind: "{modbusId}/MODBUS/{address}"
     - Ищем MODBUS устройство
     - Отображаем название MODBUS устройства и адрес на шине
```

### 7. Резолв связей допплера со скриптами

**Проблема:** Допплеры связаны со скриптами через параметр `onDoppler`, скрипты содержат действия.

**Алгоритм:**

```
Для допплера:
  1. Получаем onDoppler ID из state.onDoppler или device.onDoppler
  
  2. Ищем скрипт по ID:
     - script = allDevices.find(d => d.id === onDopplerId)
  
  3. Получаем действия скрипта:
     - actions = script.state?.action || script.action || []
  
  4. Для каждого действия:
     - Ищем устройство действия по ID
     - Проверяем привязку действия к актуатору (если есть)
  
  5. Отображаем цепочку:
     - Допплер → Скрипт → Действия
```

### 8. Резолв связей термостатов

**Проблема:** Термостаты связаны с модулями через DI каналы и с датчиками температуры через sensor.

**Алгоритм:**

```
Для термостата:
  1. Bind к DI каналу:
     - Парсим bind: "{moduleId}/di/{номер}"
     - Ищем модуль (обычно S4)
     - Получаем состояние DI канала
  
  2. Датчик температуры:
     - Получаем sensor ID из state.sensor
     - Ищем датчик по ID
     - Проверяем, что sensor.master === bind модуля
  
  3. Скрипты управления:
     - onStartHeat, onStopHeat, onStartCool, onStopCool
     - Для каждого скрипта ищем устройство по ID
```

## 🔄 Порядок выполнения резолвинга

При отображении информации об устройстве резолвинг выполняется в следующем порядке:

1. **Базовая информация** (ID, название, тип, категория, помещение)
2. **Статус устройства** (value, initialized, online, ready, ip)
3. **Параметры устройства** (temperature, humidity, co2, и т.д.)
4. **Специальные секции:**
   - Термостаты: bind к DI, sensor, скрипты управления
   - Потребители: связь с актуатором
   - Сенсоры: связь с модулем
   - NOVA: параметры приточной вентиляции
   - INTESIS_BOX: параметры кондиционера
   - MODBUS: подключенные устройства
5. **Каналы актуатора** (DO/DIM/AO/group) с обратным резолвом
6. **Специальные типы:**
   - S3/S4: датчики температуры (temperature_ext[])
   - M1: датчики протечки (DI каналы)
   - Допплеры: обработчики движения (onDoppler)

## 📊 Кэширование результатов резолвинга

Для оптимизации производительности результаты резолвинга кэшируются:

- **deviceInfoByDeviceId** - кэш полной информации об устройстве
- **devicesByMac** - кэш устройств по MAC адресу
- **knownParameters** - кэш известных параметров устройства

Кэш инвалидируется при изменении состояния устройства или его связей.
